# TO-BE процесс онбординга магазина

## 1. AS-IS (кратко)

Купленный магазин открывается 2–3 недели: ИТ-инженер едет на точку, выгружает номенклатуру
в Excel и отправляет в HQ; товаровед вручную сопоставляет ~10 000 позиций (500 позиций/час);
итоговый файл загружается в SAP ERP и ночным FTP рассылается на локальные серверы.
Человеческий фактор даёт **15% ошибок** — не бьются штрихкоды и цены.

## 2. TO-BE: пулы и роли

| Пул | Тип | Что делает |
|---|---|---|
| **Магазин** | Люди | Выгружает номенклатуру или подключает коннектор к старой кассе |
| **HQ Data Integration** | Люди | Запускает процесс, проверяет спорные позиции, публикует |
| **AI Matching Service** | Система | Нормализует, сопоставляет SKU, считает уверенность |
| **SAP ERP** | Система | Обновляет мастер-данные и публикует каталог в Cloud POS |
| **Cloud POS** | Система | Принимает каталог и обновляет данные для кассы |

## 3. BPMN 2.0 TO-BE

### Поток данных между пулами

| Откуда → Куда | Что передаётся |
|---|---|
| Магазин → HQ | файл номенклатуры (CSV/XLS) или поток из коннектора |
| HQ → AI | список позиций: название, штрихкод, цена, категория |
| AI → HQ | по каждой позиции: `SKU`, `confidence`, признак критичности |
| HQ → SAP ERP | подтверждённый маппинг |
| SAP ERP → Cloud POS | каталог: SKU, цены, штрихкоды |
| Cloud POS → Магазин | каталог получен, касса готова |
| HQ → Магазин | возврат на исправление при ошибке валидации |

### Автоматизация

- Экспорт и загрузка — коннектор или RPA для legacy-касс без API.
- Валидация формата и полноты — до запуска маппинга.
- Нормализация названий (регистр, сокращения, единицы) — до сопоставления.
- Маппинг и расчёт `confidence` — AI-сервис, а не VLOOKUP.

## 4. Точка верификации (участие человека)

Человек проверяет **только спорные позиции**, а не весь ассортимент.

**Шаг 1. XOR-шлюз «`confidence ≥ 95%` и позиция не критична?»**

| Условие | Решение |
|---|---|
| `confidence ≥ 95%` и позиция не критична | Автоматическое принятие → публикация |
| `confidence < 95%` или критичная позиция | Ручная проверка: подтверждение или исправление |

Это **human-in-the-loop**: система выполняет всё, что может, человек подключается только при исключении.

**Шаг 2. После ручной проверки — XOR-шлюз «Кандидат найден?»**

| Условие | Решение |
|---|---|
| Кандидат найден в мастер-данных | Публикация маппинга в ERP |
| Кандидата нет | Создание нового SKU (категорийный менеджмент) → публикация |

**Кандидат** — карточка товара в мастер-данных VitaStore, с которой сопоставилась позиция
из старой кассы. Если кандидата нет, товара нет в ассортименте сети — создаётся новый SKU
(внутренний ID, категория, цена, штрихкод) через категорийный менеджмент.

**Почему 95%:** ошибка маппинга дороже проверки — привязка дешёвого штрихкода к дорогому
товару даёт продажу в минус. Автоматика работает только там, где модель уверена.

**Снижение ошибок:**

- контроль полноты — число позиций до и после маппинга совпадает, пропусков нет;
- проверка дублей — один штрихкод не может быть привязан к двум SKU;
- логирование каждой автоматической позиции (модель, версия, `confidence`);
- выборочный аудит 5% автоматических решений;
- обучение модели на исправлениях товароведа.

## 5. Целевые метрики

| Метрика | AS-IS | TO-BE |
|---|---|---|
| Срок открытия магазина | 14–21 день | **≤ 5 дней** |
| Доля ручного маппинга | ~80% | **≤ 10%** |
| Ошибки маппинга | 15% | **≤ 1%** |
| Выезд ИТ-инженера | Обязателен | Не требуется |
